نفس سؤال الـ LLD المشهور، بس من غير State Pattern ومن غير objects بتغيّر في بعض. الآلة كلها step(machine, event) → [machine, effects]: function نقية بتاخد الحالة وحدث، وبترجّع حالة جديدة وقائمة بالحاجات المطلوب تنفيذها. الصفحة دي بتشغّل نفس الكود اللي عليه التستات، ومش بتخزّن state خالص: بتخزّن الـ events وتعيد تشغيلها.

    قرارات التصميم، ومقارنتها بالحل الكلاسيكي
    
      
    الحل المعتاد للسؤال ده: كلاس VendingMachine فيه selectedProduct و totalCoins و currentState، و State Pattern بأربع حالات (Idle و Ready و Dispense و ReturnChange)، وكل حالة بتعمل machine.setState(new ...). ده كويس، بس فيه حاجات أحسن:
    
    
    

    
    
      ليه function واحدة بدل State Pattern؟step(state, event)
      
    
        
      
          
    • الآلة finite state machine. والـ FSM في الأساس جدول: (حالة، حدث) ← (حالة جديدة، أفعال). الـ State Pattern بيقطّع الجدول ده على 4 كلاسات، كل واحد ماسك reference للآلة وبيغيّر فيها.
      • 
          
    • الـ switch اترفض في الحل الكلاسيكي بحجة Open/Closed. بس مع discriminated unions، الكومبايلر بيجبرك تتعامل مع كل (حالة، حدث). لو ضفت حالة جديدة ونسيت تتعامل معاها في أي مكان، الكود مش هيبني. ده أأمن من OCP، لأن الحالات هنا مجموعة مقفولة مش plugin system.
      • 
        
    
        
    نسخة OOP كويسة ممكن تقرّب جداً من ده: states immutable، وكل method بترجّع الـ state اللي بعدها بدل ما تعمل setState. الفرق اللي بيفضل إن الـ effects بتتنفذ جوه الـ method بدل ما ترجع data.
    
      
    
    
    

    
    
      ليه كل حالة شايلة بياناتها جواها؟make illegal states unrepresentable
      
    
        
      
          
    • لو selectedProduct و currentState حقلين منفصلين، تقدر تكتب آلة في Idle ومعاها منتج مختار. حالة مستحيلة، بس الكود بيسمح بيها، فلازم تفضل فاكرها في كل method.
      • 
          
    • هنا idle مالهاش أي بيانات، و paying معاها slot و inserted. الحالة المستحيلة ماينفعش تتكتب أصلاً.
      •

      إرجاع الباقي حالة ولا فعل؟effects as data
      
    
        
      
          
    • ReturnChangeState مش مكان الآلة بتقف فيه، ده حاجة بتعملها. هنا بقى effect: { tag: 'returnCoins', coins }.
      • 
          
    • الـ core مش بيلمس hardware خالص، بيرجّع قائمة. الـ shell (الصفحة دي، أو driver حقيقي) هو اللي ينفّذ. وده اللي خلّى التستات تقرا الـ effects زي أي قيمة، والصفحة تعملها animation.
      • 
          
    • dispensing حالة حقيقية فعلاً، بس لسبب مختلف: الآلة مستنية تأكيد من الـ sensor، والفلوس محجوزة في escrow لحد ما المنتج ينزل.
      • 
        
    
      
    
    
    

    
    
      طب لو المنتج اتزنق؟ مين يعمل rollback؟commit on confirmation
      
    
        
      
          
    • ولا حد، لأن مفيش حاجة اتغيرت. المخزون والصندوق مش بيتلمسوا غير لما event اسمه dispensed يوصل من الـ sensor.
      • 
          
    • لو وصل jammed، الآلة بترجع idle وبترجّع نفس العملات اللي اتحطت بالظبط. مفيش transaction ولا compensation: الـ atomicity جاية من التصميم نفسه.

      ليه الفلوس عملات مش رقم؟CoinCounts, not totalCoins
      
    
        
      
          
    • totalCoins = 135 مش بيقولك تقدر ترجّع 35 قرش ولا لأ. لازم تعرف الصندوق فيه كام عملة من كل فئة. من غير كده حالة "Exact change only" مش هتلاقي ليها مكان في التصميم.
      • 
          
    • الـ greedy (ابدأ بأكبر عملة) بيفشل مع مخزون محدود: 30 قرش من {25، 10، 10، 10} مفيش 5 تكمّل بيها الـ 25. makeChange بيبدأ greedy وبيرجع خطوة لو اتزنق، فبيلاقي 10+10+10. شوف سيناريو "باقي صعب".

      إزاي الصفحة بتعمل time travel؟state = replay(events)
      
    
        
      
          
    • الصفحة مش بتخزّن الآلة. بتخزّن الآلة اللي بدأت بيها وقائمة الـ events، ومع كل رسمة بتنادي run(start, events) وتعرض اللحظة اللي إنت واقف عليها.
      • 
          
    • ارجع لأي لحظة واكبس أي زرار، هيتعمل فرع جديد من النقطة دي. ده event sourcing ببلاش، و undo ببلاش، وأي bug report ممكن يبقى مجرد قائمة events تعيد تشغيلها.
